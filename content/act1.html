Act I · ping google.com

Enter

Under the Enter key is a switch. Pressing it connects one row wire to one column wire in a grid that runs under every key.

The keyboard has its own small computer, a microcontroller, which checks that grid about a thousand times a second. When it sees the row and column connect, it doesn't believe it right away. Metal contacts bounce for a few milliseconds, so it waits for the signal to settle.

A keyboard can't speak first

USB is polled. The keyboard waits until the computer's USB host controller asks whether it has anything to say, which happens every 1 to 8 milliseconds depending on the keyboard.

The answer is an 8-byte report: a byte of modifier keys (Shift, Ctrl and so on), a reserved byte, and up to six keys that are down right now. Enter is 0x28.

00 00 28 00 00 00 00 00

An interrupt

The host controller copies the report into main memory on its own (direct memory access) and raises an interrupt: a signal that makes a CPU core stop what it was doing, save its place, and run the kernel's handler for that device.

About 6 milliseconds have passed. Nothing has touched the network yet, and nothing will for a while.

More detail

Gaming keyboards poll at 1,000 Hz or faster and debounce more aggressively, so press-to-report can be under 2 ms. Bluetooth keyboards add their own radio schedule and are usually slower. The host controller here is xHCI, the standard USB 3 controller interface; it keeps rings of work in memory that the driver and the hardware both read and write.

To the shell

The kernel's USB HID driver reads the report, compares it with the previous one, and finds a new key: Enter went down. It turns that into an input event, KEY_ENTER, value 1, readable from a device file like /dev/input/event3.

Which window gets it?

Your desktop's compositor (on most Linux desktops now, a Wayland compositor) reads that event. It knows which window has keyboard focus, so it forwards the key there, to the terminal emulator.

The terminal emulator turns Enter into one byte, a carriage return (\r, 0x0D), and writes it into the pseudo-terminal, or PTY: a pair of connected ends, one held by the terminal emulator and one by the shell running inside it.

bash

bash has been waiting on the other end, reading one byte at a time. While you typed, its line editor (readline) echoed each character back so it showed up on screen. A carriage return means the line is finished.

bash now has the string ping google.com, less than a millisecond after the interrupt.

More detail

The kernel's tty layer sits between the PTY's two ends. In its normal (canonical) mode it collects a whole line and handles Backspace itself. readline turns that off so it can do its own editing, history and tab completion. The same layer is what turns Ctrl-C into a SIGINT signal for whatever is running.

A new process

bash splits the line into words: ping and google.com. ping isn't one of bash's own commands, so it has to be a program on disk. bash checks its cache of programs it has run before and, if that misses, tries each directory in $PATH until it finds /usr/bin/ping.

fork

To run a program, Unix first copies the process that wants to run it. bash calls fork() (on Linux, the clone system call) and the kernel makes a second bash: same memory, same open files, new process ID.

The memory isn't actually copied yet. Both processes share the same memory pages, marked read-only, and the kernel copies a page only when one of them writes to it.

exec

The child calls execve("/usr/bin/ping", ...). The kernel throws away its copy of bash, reads the start of the file, and finds an ELF program that needs a dynamic linker. It maps the program and the linker into memory, the linker maps the shared libraries ping needs (the C library among them), and ping's main() runs.

The parent bash waits. Your prompt comes back when the child exits.

More detail

Why copy and then replace, instead of one call? The child can change things in between: point its output at a file, join a pipe, move to another directory. That gap is how ping google.com > out.txt works. Linux systems also offer vfork and posix_spawn, which skip most of the copying; posix_spawn takes a list of redirections to make in between.

Finding google.com

ping can't send anything to a name. It calls getaddrinfo("google.com") in the C library, which reads /etc/nsswitch.conf to see where to look: the local /etc/hosts file first (nothing there), then DNS.

On many Linux systems, DNS questions go to a small local service, systemd-resolved, at 127.0.0.53. It keeps a cache. Say it's empty, and so is the cache at your ISP's resolver, which it passes the question to. Each question is a small UDP packet to port 53.

Ask the root

With nothing cached, the resolver starts at the top. DNS has 13 root server names, a.root-servers.net through m, run by 12 organizations. Each name is served from many places at once: about 2,000 machines around the world share those 13 addresses, and ordinary internet routing delivers your question to a nearby one. That's called anycast.

The root doesn't know google.com. It answers with a referral: here are the servers for .com.

Ask .com

The .com servers (run by Verisign, also anycast) don't know google.com's address either, but they know who does: ns1.google.com through ns4. They include those servers' addresses in the answer, since otherwise you'd need google.com to find google.com.

Ask Google

Google's own nameserver answers with six addresses, each good for 300 seconds, and ping takes the first: 172.253.124.113. Google hands out different addresses depending on where the question comes from, so this one is a front end near Atlanta, a few hundred kilometres from the house.

Every layer caches what it learned on the way back, and ping prints its first line:

$ ping google.com
PING google.com (172.253.124.113) 56(84) bytes of data.

This was the slow path. Usually a cache already has the answer: the one on your laptop in well under a millisecond, or your ISP's in a few milliseconds.

More detail

ping asked for IPv6 addresses too. On a network with working IPv6, the C library would usually put the IPv6 address first and the rest of this story would run over IPv6: longer addresses, ICMPv6 instead of ICMP, and no NAT at the router.

Google picks the address from where the question seems to come from: the resolver's address, or a truncated piece of yours if the resolver passes it along (EDNS Client Subnet).

Building the packet

ping speaks ICMP, the Internet Control Message Protocol, the same protocol routers use to report problems. ping only needs two of its message types: echo request (8) and echo reply (0).

On a modern Linux system, ping doesn't need root. It opens an unprivileged "ping socket" (socket(AF_INET, SOCK_DGRAM, IPPROTO_ICMP)), writes an 8-byte ICMP header and 56 bytes of data (the time, then filler), and calls sendto(). That system call is the line between ping and the kernel.

ICMP, then IP

The kernel puts the socket's identifier into the ICMP header and computes its checksum. Then it wraps those 64 bytes in a 20-byte IPv4 header: version, length, a time to live of 64, protocol 1 for ICMP, and the two addresses.

Where to? The routing table says 172.253.124.113 isn't on the local network, so it goes to the default gateway, the router at 192.168.1.1, out the Wi-Fi interface.

The next hop

Wi-Fi and Ethernet deliver to hardware addresses, not IP addresses. The kernel's neighbour table already has the router's, from an ARP broadcast (who has 192.168.1.1?) the first time it needed it. A 14-byte Ethernet header goes on the front. The packet is done: 98 bytes.

Out of the machine

The frame joins a queue (Linux's Wi-Fi layer keeps one for each device it talks to, so one busy program can't starve the others), and the driver points the network card at it in memory. The card copies it out on its own and takes it from there.

From sendto() to the card: a few tens of microseconds. The send time is already in the data; ping wrote it there just before.

More detail

The Internet checksum is a one's-complement sum of the header's 16-bit words. It's cheap enough that every router updates it after changing the time to live. ICMP has its own checksum over the ICMP header and data.

The IP identification field only matters for putting split packets back together. Linux leaves it 0 here: the Don't Fragment flag is set and ping's socket isn't tied to one address. 56 data bytes is ping's default because 56 + 8 = 64.

Into the air

Before the card fetches the frame, Linux's Wi-Fi layer swaps the Ethernet header for an 802.11 header, which carries three hardware addresses instead of two, plus a short header saying the payload is IPv4. Then the card encrypts the payload with the key the laptop agreed on with the router when it joined the network (WPA2 or WPA3, both AES).

Waiting its turn

Every device in the house shares one radio channel, and only one can talk at a time. So the card listens first. If the channel is busy, it waits. When it goes quiet, it waits a random number of short slots more, so two devices that were both waiting don't start at the same instant.

This time the phone gets the channel first. The laptop waits it out, then counts down its own random wait and goes.

On the air

Wi-Fi 6 splits its channel into hundreds of narrow subcarriers and sends a few bits on each at once, coded in the wave's amplitude and phase. With 1024-QAM, every point on that grid of possibilities stands for 10 bits.

The frame takes tens of microseconds on the air, most of it a preamble the receiver uses to lock on. The router checks it and sends back an acknowledgement. If that doesn't arrive, the card tries again.

More detail

Wi-Fi uses 2.4, 5 and 6 GHz bands with channels 20 to 160 MHz wide (320 MHz on Wi-Fi 7, which also goes up to 4096-QAM: 12 bits a point). At 5 GHz the wavelength is about 6 cm. How many bits each subcarrier carries changes constantly with signal quality; the 1024 grid needs a strong, clean signal.

The router

The router decrypts the frame, takes off the Wi-Fi header, and reads the IP destination. It isn't anyone in the house, so the packet goes out the other side, toward the internet.

NAT

Every device in the house has a private address like 192.168.1.23. Those mean nothing outside, and the house has one public address. So the router rewrites the source to its own public address, 203.0.113.7, and writes down what it did: ICMP from 192.168.1.23, identifier 23582, to 172.253.124.113. When a reply comes back with that identifier, it'll know who it's for.

It also lowers the time to live from 64 to 63, as every router does, and fixes the IP checksum.

Light

The router hands the packet to the fiber terminal on the wall, which turns it into pulses of laser light. Fiber to the home is usually a passive optical network: one strand from the street is split among dozens of homes, so they take turns sending, each in time slots the ISP's equipment assigns. The packet waits for the house's slot, a fraction of a millisecond, then goes.

The light stays inside a glass core about 9 microns across and travels at about two thirds of its speed in a vacuum.

Across the internet

At the ISP the light becomes packets again and passes from router to router. Each router does the same small job very fast: find the longest matching prefix for the destination in its table, subtract one from the time to live, send the packet out the right port. Big routers do it in custom chips, billions of packets a second.

This ISP hauls traffic from Asheville to its core in Charlotte first. Light in fiber covers about 200 km per millisecond, and fiber rarely runs straight.

Who knows the way?

No router knows the whole internet. They know prefixes. Google's network, AS15169, announces the address blocks it owns to the networks it connects to, using BGP, and those announcements spread from network to network. The ISP's routers learned that the block holding 172.253.124.113 is reached through a connection to Google in Atlanta.

Google's network

The ISP hands the packet to Google in Atlanta, and Google's own fiber carries it the rest of the way to the front end that owns the address. Google connects directly to most large ISPs, close to their customers, so the trip usually doesn't cross anyone else's network.

About 5 milliseconds after leaving the house, it arrives.

More detail

traceroute google.com shows the path by abusing the time to live: it sends packets with TTL 1, then 2, then 3, and each router that drops one at zero sends back an ICMP "time exceeded" message, revealing itself. Many routers inside large networks don't answer, which is why traceroutes are full of asterisks.

Google answers

Inside Google's edge, routers often have several equally good paths to the next stage. They pick one per flow by hashing the packet's addresses, so a flow stays on one path while the load spreads across all of them (equal-cost multipath, ECMP).

Load balancers

For web traffic the next layer is Maglev, Google's software load balancer: a fleet of ordinary servers that spread connections across the front ends, using consistent hashing so any of them sends a connection's packets to the same place. Google doesn't say which machines answer pings. Some machine answering for 172.253.124.113 receives the echo request.

The reply

Answering a ping is cheap: change the type from 8 to 0, swap the source and destination addresses, keep the identifier, sequence number and data exactly as they arrived, fix the checksum, and send it back. The timestamp ping wrote goes home untouched.

Microseconds of work. Nearly all of the round trip is distance.

The way back

The reply makes its way the same way, router by router, but nothing makes it take the same route. Each direction is routed on its own, so a reply can enter the ISP somewhere else or take a different path inside it. This one comes back through Greenville.

Home

Downstream on the fiber, the ISP sends to every home on the strand and each terminal keeps only its own traffic. The router looks up identifier 23582 in its NAT table, rewrites the destination back to 192.168.1.23, and sends the reply over Wi-Fi to the laptop.

Back inside

The laptop's Wi-Fi card receives the frame, acknowledges it, decrypts it, and copies it into a buffer the driver set aside in memory. Then it raises an interrupt. The kernel's handler does almost nothing except schedule the real work, which then polls the card for anything else that arrived meanwhile (NAPI). Under heavy traffic, that's much cheaper than an interrupt per packet.

Up the stack

The kernel takes the layers off in reverse. Ethernet says IPv4. IP says it's for this machine and the checksum is fine. ICMP says echo reply, identifier 23582, which belongs to ping's socket. The data goes into that socket's receive queue with the time it arrived.

The reply, as it arrives. Compare it with the request: type 0, the addresses swapped, a time to live of 117, and the same 56 bytes of data.

Wake up, ping

ping has been asleep since it sent the request, blocked in recvmsg() on its socket with a timeout set. The scheduler marks it runnable and soon puts it on a CPU core. It reads the reply, checks the data came back intact, and pulls its send time out of the payload.

Received minus sent: 11.8 ms.

64 bytes from

Before printing, ping asks DNS one more question, backwards this time: what's the name for 172.253.124.113? (ping -n skips this.) The answer is ys-in-f113.1e100.net. 1e100 is a googol, the number Google is named after.

Then it formats the line and writes it to standard output, which is the PTY. The kernel passes the bytes to the other end, where the terminal emulator is waiting.

$ ping google.com
PING google.com (172.253.124.113) 56(84) bytes of data.
64 bytes from ys-in-f113.1e100.net (172.253.124.113): icmp_seq=1 ttl=117 time=11.8 ms

64 bytes is the ICMP part: header plus data. ttl=117 is what was left of the reply's time to live; if Google started it at 128, it passed 11 routers.

The terminal draws

The terminal emulator parses the bytes, updates its grid of character cells, and redraws the changed ones. Each character is a small image (a glyph) rendered from the font once and kept in a texture, so drawing a line of text is mostly copying. Many terminals do this on the GPU now. The finished window goes to the compositor.

The screen

The compositor combines the windows into one frame and gives it to the display controller, which sends it to the screen on the next refresh. At 60 Hz that's a wait of up to 16.7 ms. The panel updates from top to bottom, row by row, and each pixel takes a few more milliseconds to settle.

You

Light from the screen reaches your eyes in under two nanoseconds. Noticing the new line takes you something like 200 milliseconds. The trip to Google and back took 11.8.

Then ping sleeps for a second and sends icmp_seq=2. It already has the address this time.
