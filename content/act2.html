Now type claude

That was the classic version. Everything in it still happens, constantly, underneath everything else.

Here's the newer one. Same laptop, same terminal, same internet. Instead of ping google.com, you start Claude Code and ask it something. Most of Act I happens again in the first few milliseconds, and then the interesting part happens somewhere else.

claude starts

The key matrix, USB, the interrupt, the PTY, bash, fork and exec all happen exactly as before. The program is different: claude is a single program file of about 290 MB. Claude Code is written in TypeScript (JavaScript with type checking) and compiled with Bun, which packs everything needed to run JavaScript into that one file, next to the app.

Your setup

It reads its settings, then your CLAUDE.md files (instructions you've written for it, for all projects and for this one), any saved memory, and the skills and plugins you've installed (add-ons that bring extra instructions and tools). It starts the MCP servers you've configured. These are small programs that give it more tools. Some run on your machine and some are servers elsewhere that it connects to.

More detail

A local MCP server is a child process: Claude Code starts it and talks to it over pipes, its standard input and output. A remote one is a connection to a server over the network.

Raw mode

Then it switches the terminal to raw mode, so every key comes straight through instead of a line at a time. Then it draws its interface. That's built with React, a library usually used for web pages, and Ink, which draws it as rows of text in the terminal instead. You type your prompt and press Enter.

The clock starts over here.

Assembling the request

The model doesn't remember anything between requests. Every time, Claude Code sends everything it needs to see to the Messages API, the service programs use to talk to Claude. It goes as one JSON document, a plain-text format for labeled data. It names the model and holds a system prompt (Claude Code's standing instructions), the tools the model may use, the conversation so far, and settings such as a cap on the reply's length and "stream": true, which asks for the reply to come back piece by piece.

Before your words

Most of it is there before you type anything. The system prompt explains how Claude Code works and what it can do on your machine. Every built-in tool comes with a description and a JSON Schema, an exact list of the inputs it takes. The tools run commands, read and edit files, search, and start subagents (helpers that take on part of a task in a conversation of their own). Tools from your MCP servers go in as just their names until Claude needs one. Your CLAUDE.md files, saved memory and a few facts about your environment go in too. Together that's typically tens of thousands of tokens.

A token is the unit the model reads: a short word, a piece of a longer one, punctuation. For Claude, an English token averages about three characters; the exact count depends on the model.

Your message

Your message goes at the very end. On the first turn of a session it's often around 1% of the request. On later turns the conversation so far sits in between, and it grows every time.

Marked for reuse

Most of the request matches one Claude Code sent recently: the same tools, system prompt and project files, and on later turns the whole conversation so far. Claude Code marks where that matching start ends (a cache breakpoint). The API saves the work it did reading everything before the mark, so a later request that starts the same way can skip it. That's prompt caching. The saved work lasts 5 minutes, or an hour, which Claude Code asks for on a subscription. The API reads the request in a fixed order, tools, then system prompt, then messages, and one changed byte means redoing everything after it.

Over the wire

Act I again, mostly. The name is api.anthropic.com and DNS answers 160.79.104.10, an address in a block registered to Anthropic (AS399358) and reached through Cloudflare's network. If Claude Code doesn't have a connection open already, it opens one. First comes TCP, the protocol that makes sure every byte arrives, in order. It sets up the connection with a handshake (one round trip). Then TLS 1.3 sets up encryption (one more): the two sides agree on keys, and Claude Code checks the server's certificate, which proves it's really talking to api.anthropic.com.

The request

On a first turn the JSON is around 100 KB. TCP cuts it into about 70 pieces of up to 1,460 bytes, each in its own packet, and doesn't send them all at once. A new connection starts cautiously: about 14 KB in the first round trip, then twice as much each round trip after that, as long as nothing gets lost. Inside the encryption it's an ordinary web request: POST /v1/messages.

More detail

TCP calls those pieces segments, and the cautious start is slow start: the first round trip carries ten segments, about 14 KB. The request is HTTPS (HTTP inside TLS), sent over HTTP/2. POST means it carries data to the server, and /v1/messages is the API's address for it.

Same packets

Each of those packets is built like Act I's: an IP header, then TCP where the ICMP header was, then a slice of encrypted request. The routers on the way can't read the request and don't need to. They read the headers, subtract one from the time to live, and pass it on, same as before.

The front door

The first machines to touch the request are Cloudflare's, at a site near you. They're the far end of the encrypted connection: they decrypt the request and pass it on toward Anthropic's servers. So far this is the same as many large web services.

Who's asking

The request carries proof of who sent it: an API key, which is a long secret string, or for a Claude subscription, a token Claude Code got when you logged in through your browser (with OAuth). The API checks it, looks up the limits that apply to you (requests and tokens per minute for an API key, a five-hour and a weekly allowance for a subscription), and keeps count.

Where to run it

Then the request goes to one of the groups of machines running the model you asked for, one with room for it, where it may wait in a short queue. This is where it leaves the part of the internet that looks like Act I.

A building full of chips

The model runs on accelerators: chips built mostly for one kind of arithmetic, multiplying matrices, which are big grids of numbers. Each has a large slab of silicon at the center, the die, surrounded by stacks of fast memory that can feed it terabytes per second. The die holds grids of thousands of tiny units that each multiply two numbers and add the result to a running total.

More detail

The fast memory is high-bandwidth memory (HBM), stacked right beside the die. In a TPU, numbers flow through a grid of multiply-and-add units in waves, each unit passing its result to the next. That design is called a systolic array.

A server

Several chips share a server, joined by links much faster than ordinary networking so they can work almost as one. A frontier model, one of the largest and most capable kind, is generally too big for one chip's memory. Its weights, the numbers learned in training, are split across many chips, and each does part of every calculation and trades partial results with the others.

Racks, rows, halls

Servers stack into racks, racks line up in rows, rows fill halls. Each running copy of the model uses a group of chips, and a building runs many copies, each serving many conversations at once.

A campus

Anthropic runs Claude on three kinds of chips: Google's TPUs, Amazon's Trainium and NVIDIA's GPUs. The numbers are large. In October 2025 Anthropic announced access to up to a million TPUs, with well over a gigawatt of capacity coming online in 2026. Amazon's Project Rainier, which Anthropic uses to build and run Claude, opened in October 2025 with nearly half a million Trainium2 chips. A gigawatt is roughly the output of a large power plant.

Reading the prompt

The text is cut into tokens, and each token becomes a vector: a long list of numbers the model learned for it in training. Your request is now a long list of vectors, one per token, tens of thousands of them.

Every layer, all at once

The model is a kind called a transformer: a stack of layers, dozens deep, and every token passes through every layer. In each layer, attention lets every token look back at the tokens before it and take in what's relevant. Then a second part, the feed-forward block, works on each token on its own. Both are mostly matrix multiplication. The whole prompt is known up front, so all its tokens move through each layer together, which keeps the chips busy. This stage is called prefill.

Mostly from cache

As it goes, each layer saves two vectors per token, a key and a value, which later tokens use when they look back. That's the KV cache. For the part of your request that matches a recent one, those keys and values already exist, so only the new part runs: your message, and anything else after the breakpoint. That's a big part of why the first token can be ready in about a second.

More detail

A rule of thumb: one token through a model costs about two arithmetic operations per parameter. Anthropic doesn't publish Claude's size, but for a model with hundreds of billions of parameters, 25,000 tokens from scratch is on the order of 1016 operations, many chip-seconds of work even split across a group of chips. With the prefix cached, it's a small fraction of that.

One token at a time

At the top of the stack, the last token's vector becomes a score for every token the model knows (its vocabulary). The scores become probabilities: how likely each token is to come next. One token is picked, the likely ones more often than the unlikely ones. That's the next token of the reply.

And again

To get the one after it, that token goes back in at the bottom and runs through every layer, looking back at everything before it through the KV cache. One full pass per token, each waiting on the last. This stage is called decode. Per token, it's slow work for the chips. Each pass reads billions of the model's weights from memory to make a single new token, and most of the time goes to waiting on memory.

Not alone

So the chips don't decode one conversation at a time. Each step makes the next token for a whole group of conversations at once (a batch), and reads the weights once for all of them. Yours is one of many moving through the same chips in the same moment.

Thinking, then answering

Current Claude models often think before answering: a run of tokens worked through first, then the reply itself. They come out at dozens of tokens a second. You don't get the thinking word for word; at most you see a summary of it. Each token of the reply is sent home as soon as it exists.

Streaming back

The answer comes back over the same connection a piece at a time, in a format called server-sent events. Each event is two lines of plain text: an event: line naming what kind it is, and a data: line with the details as JSON. Every new piece of the reply is one event:

event: content_block_delta
data: {"type":"content_block_delta","index":1,
  "delta":{"type":"text_delta","text":"Love this"}}

event: ping

event: ping
data: {"type": "ping"}

Mixed into the stream are ping events. They carry nothing. The docs don't say why they're there, but the usual reason is to keep a quiet connection from looking idle, so nothing in between gives up on it. Act I's question shows up again, forty-odd years later, as a heartbeat inside Act II.

On your screen

Claude Code reads the events as they arrive and adds the new text to the reply. The reply is in Markdown, plain text with marks like **bold**, so Claude Code formats it and redraws its part of the terminal. From there every character takes the path from the end of Act I: a write to the PTY, the terminal emulator, the compositor, the next refresh, your eyes.

The loop

Often the reply doesn't end with an answer. It ends with a request to use a tool:

{"type": "tool_use", "name": "Bash",
 "input": {"command": "ping -c 1 google.com"}}

The response also says why the reply stopped: its stop_reason is "tool_use". The model can't run anything itself. It asks.

Your machine does that part

Claude Code checks the command against your permission settings and asks you if it has to. Then it runs it, and for this command that means Act I again, minus the keyboard and the screen. Well under a tenth of a second later it has the output.

And back again

It adds the output to the conversation as a tool_result and sends a new request with all of it: the tools, the system prompt, every message so far, the new result. The API doesn't remember anything between requests, so every turn sends everything again. Prompt caching is what makes that affordable: everything before the new part matches the last request, so that work is already done.

Many laps

A real task takes dozens or hundreds of these round trips: read a file, edit it, run the tests, read the error, edit again. The conversation grows every lap. A model can only take in so many tokens at once, its context window, and when the conversation nears that limit Claude Code compacts it into a summary and carries on. Subagents run loops of their own, in parallel, each with its own context.

Act I keeps happening inside Act II: every web request, package download and test that touches the network.

Scale

And that's one person. Requests like yours arrive from everywhere at once, all landing on the same kind of machinery.
